# Funny: парсер HW2 и семантический анализ HW3

Java 17, рекурсивный спуск, AST, восстановление после синтаксических ошибок и проверка имён и типов. Реализован бонус HW3: вывод типов локальных переменных по первому корректному присваиванию. Зависимостей времени выполнения нет, JUnit нужен только для тестов.

## Запуск

Из папки `parser`:

```sh
mvn clean test
java -cp target/classes ru.nsu.naboka.Main examples/types-positive.funny
java -cp target/classes ru.nsu.naboka.Main examples/types-negative.funny
java -cp target/classes ru.nsu.naboka.Main < examples/minimal.funny
java -cp target/classes ru.nsu.naboka.Main --parse-only examples/positive.funny
```

Без аргументов читается стандартный ввод, с одним аргументом — файл UTF-8. По умолчанию после успешного разбора запускается семантический анализ. В stdout выводится аннотированный AST в S-выражениях, в stderr — все найденные ошибки в формате `строка:столбец: [КОД] сообщение`. Коды завершения: 0 — успех, 1 — ошибки языка, 2 — неверные аргументы или ошибка чтения файла.

Флаг `--parse-only` сохраняет режим HW2: только обычный AST, например `(+ 1 (* 2 3))`, и ошибки лексера/парсера. При синтаксических ошибках семантический этап не запускается, выводится частичный обычный AST. При семантических ошибках выводится аннотированный AST с типом `error` у некорректных выражений; его нельзя передавать в генерацию кода.

Для автономного запуска тестов при уже загруженных зависимостях можно использовать `mvn -o clean test`.

## Интеграция с первой работой

Maven компилирует исходники текущего модуля и соседнего `../regex_dfa/main/java`, подключённого как дополнительный корень исходников через `build-helper-maven-plugin`. Папки `parser` и `regex_dfa` должны лежать рядом. Код построения автоматов не скопирован и не изменён: используются `RegexToNFA`, `NFA`, `SubsetConstruction`, `Hopcroft`, `DFA`, `TokenSpec`.

В IntelliJ IDEA откройте `parser/pom.xml` как Maven-проект. После изменения POM выполните **Reload All Maven Projects** в окне Maven, затем запустите тесты. Это подключит и `src/main/java`, и `../regex_dfa/main/java`; иначе сборщик IDEA может сообщить `package ru.naboka.traver does not exist`.

Лексер один раз строит минимизированный ДКА по правилам Funny, затем сканирует с максимальным совпадением и запоминанием последнего принимающего состояния. Старая JSON-таблица не подходит целиком: в HW2 добавились `:`, `;`, `|`, `=>`, `->` и новые ключевые слова. Пробелы и комментарии пропускаются с учётом позиций. EOF — отдельный токен. Смещения отсчитываются от 0, строки и столбцы — от 1; CRLF считается одним переводом строки, табуляция — одним столбцом.

Идентификаторы соответствуют добавленной спецификации: латинская буква, далее буквы и цифры. Подчёркивания, разрешённые в HW1, здесь не допускаются. Правило целых чисел сохранено из HW1: `0|[1-9][0-9]*`; `01` даёт два токена и отклоняется при разборе выражения. Алфавит — ASCII, неподдерживаемый символ вызывает диагностику и пропускается.

## Особенности грамматики

Основная форма функции — `f(x: int) returns r: int { ... }`, как в спецификации. Дополнительно разрешено `function f(...)`, чтобы сохранить совместимость с HW1. Формулы имеют вид `p(x: int) => x > 0`; после определения можно поставить `;`, хотя спецификация его не требует. Пропущенные `requires` и `invariant` заменяются на `true`, пропущенное `ensures` — на `false`. Если ключевое слово контракта написано, после него нужен предикат.

Выражения разбираются по уровням приоритета с одним текущим токеном. Общий разбор выражений устраняет конфликт между `(x + 1) < 5` и `(x < 5)`. После построения поддерева проверяется его синтаксическая категория: арифметика, условие или предикат. Например, `r = true`, `if (p())` и импликация в `assert` отклоняются. В условиях разрешена импликация, в предикатах — ссылки на формулы и кванторы. Узел `Call` означает вызов функции в арифметике и ссылку на формулу в предикате; разрешение имён относится к семантическому анализу.

`else` относится к ближайшему незавершённому `if`. Этот известный конфликт исходной грамматики решается явным правилом выбора; полный синтаксис с необязательным `else` не объявляется формально LL(1). Остальной разбор предиктивный, без перебора альтернатив и отката.

`a[i] = v` сразу преобразуется в присваивание `a = set(a, i, v)`: в AST появляется узел `Update`, который принтер показывает как `set`. Он обозначает новый массив, а не изменение старого. Вложенное обновление преобразуется в `a = set(a, i, set(a[i], j, v))`; его допустимость по типам проверяется позже. `set` — внутренний узел AST, а не добавленная функция языка.

Парсер сохраняет синтаксис HW2 и не выполняет программу. После него `SemanticAnalyzer` проверяет существование и уникальность имён, типы, неизменяемость параметров, число аргументов и результатов, а также выводит типы локальных переменных.

## Семантика HW3

Поддерживаются `int`, `int[]`, логический тип `bool` для предикатов и условий, сигнатуры функций и кортежи нескольких результатов. Явные аннотации в синтаксисе HW2 — только `int` и `int[]`; они обязательны для параметров, результатов и переменных кванторов. У переменной из `uses` аннотацию можно опустить: тип `int`, `int[]` или `bool` определяется первым корректным присваиванием и затем не меняется. Например:

```text
f(a: int[]) returns r: int uses b, n {
  b = a;
  n = length(b);
  r = n;
}
```

Здесь `b: int[]`, `n: int`. Неизвестное имя, чтение локальной без аннотации до её присваивания, несовместимое последующее присваивание и невозможность вывода типа являются ошибками.

Функции и формулы имеют общую глобальную таблицу. Предварительный сбор сигнатур разрешает вызовы вперёд и рекурсию. У каждой функции своя область параметров, результатов и локальных переменных. Повторения имён в ней запрещены. В `requires` доступны параметры, в `ensures` — параметры и именованные результаты, в теле — также локальные. Квантор создаёт вложенную область. Его переменная видна только в теле квантора и должна иметь имя, отличное от имён видимых переменных.

Параметры доступны для чтения с начала функции и неизменяемы, включая обновление элементов параметра-массива. Локальные с явным типом и именованные результаты доступны для чтения с момента объявления. Локальную без аннотации нужно присвоить на каждом пути к её чтению. Содержимое `requires`, `ensures`, `invariant`, `assert` и `assume` проверяется по именам и типам.

Арифметика и сравнения порядка требуют `int`; логические операции — `bool`. Равенство разрешено между одинаковыми простыми типами. Индекс массива и новый элемент имеют тип `int`, `length` имеет сигнатуру `func(int[])->(int)`. Групповое присваивание проверяет число и типы результатов вызова. Неявных приведений и перегрузок нет.

Сохранены синтаксические категории HW2: например, `r = true`, `assert flag` и `if (p())` отвергаются парсером. Логический тип локальной переменной можно получить из вызова формулы и использовать в разрешённом грамматикой сравнении. Строки, многомерные массивы, объявления внутри блока и функции как значения не поддерживаются.

## Аннотированный AST

Формат версии 1:

```text
(typed-ast 1 (symbols ...)
  (module ... (: int @1:25 _ 1) ...))
```

Каждое выражение обёрнуто в `(: ТИП @СТРОКА:СТОЛБЕЦ СИМВОЛ ВЫРАЖЕНИЕ)`. `СИМВОЛ` — `#id` для разрешённого имени/вызова, `_` для остальных выражений. Таблица содержит записи `(symbol #id kind name TYPE @line:column)`; тип сигнатуры записывается как `(func (ТИПЫ_АРГУМЕНТОВ) (ТИПЫ_РЕЗУЛЬТАТОВ))`, нескольких результатов — `(tuple int int[])`. У объявлений переменных также печатаются итоговый тип, позиция и `#id`. Полный эталон: `examples/minimal.typed.ast`.

API для HW4: `SemanticAnalyzer.analyze(parsed.module())` возвращает исходное дерево и неизменяемые таблицы `types`, `bindings`, `symbols`, `diagnostics`. Метод `typeOf(expr)` возвращает тип выражения, `typeOf(variable)` — итоговый тип объявления. Таблицы привязаны к идентичности узлов, поэтому нужно использовать объекты исходного AST. Подробности и пример подключения приведены в отчёте.

## Ошибки и тесты

После ошибки внутри блока пропускаются токены до `;`, `}`, начала управляющего оператора либо следующего определения. На верхнем уровне разбор продолжается с определения функции или формулы. При ошибках AST может содержать только успешно разобранные части; его нельзя считать корректной программой.

`mvn test` проверяет все операторы, формулы, кванторы, контракты по умолчанию, групповые присваивания, обновление массивов, приоритеты, ассоциативность, позиции с CR/LF/CRLF, границы ключевых слов, максимальное совпадение, пустой ввод и ошибки скобок/типовых аннотаций/операторов. AST минимальной программы сравнивается с `examples/minimal.ast`. Для ошибочного `examples/negative.funny` ожидаются диагностики из `examples/negative.errors`. Есть проверка восстановления и 500 случайных повреждённых входов с ограничением времени.

Для знакомства с реализацией удобно читать файлы в порядке: `Token`, `Lexer`, `Ast`, `Parser`, `AstPrinter`, `Main`.

Тесты HW3 отдельно проверяют области видимости, повторные объявления, включая переменные кванторов, вызовы вперёд, рекурсию, неизменяемость параметров, типы операций и контрактов, массивы, несколько результатов, чтение типизированных переменных до присваивания, вывод типов и продолжение после ошибок. Отрицательный пример сравнивается с `examples/types-negative.errors`, аннотированное дерево — с `examples/minimal.typed.ast`. Старый `examples/positive.funny` является положительным примером синтаксиса HW2; он намеренно не удовлетворяет всем семантическим проверкам HW3, поэтому для него используется `--parse-only`.
