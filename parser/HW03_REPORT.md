# HW3. Семантические проверки и типы

## Что реализовано

Семантический анализ встроен после парсера HW2 и использует его AST без изменения структуры узлов. Реализованы таблицы символов, области видимости, проверка объявлений и присваиваний, типизация всех выражений и операторов, проверка сигнатур, накопление диагностик и аннотированный AST. Дополнительно выполнен бонус: вывод типов локальных переменных без аннотации.

Запуск из каталога `parser`:

```sh
mvn clean test
java -cp target/classes ru.nsu.naboka.Main examples/types-positive.funny
java -cp target/classes ru.nsu.naboka.Main examples/types-negative.funny
```

## Области видимости и порядок анализа

Первый проход собирает сигнатуры функций и формул в общую глобальную таблицу. Это позволяет вызывать определения, расположенные ниже, и поддерживает взаимную рекурсию. Повторное объявление глобального имени запрещено; перегрузок нет. Встроенная функция `length` добавляется в эту же таблицу.

Второй проход проверяет каждое определение. Параметры объявляются до `requires`, результаты — до `ensures`, локальные из `uses` — до тела. Параметры, результаты и локальные одной функции не могут иметь одинаковые имена. У разных функций независимые области. Локальное имя может затенить глобальную функцию: попытка вызвать его тогда даёт `NOT_CALLABLE`.

Каждый квантор создаёт дочернюю таблицу для своей переменной. Затенение внешнего имени разрешено, выход из квантора восстанавливает внешнюю привязку. Блоки и ветви также проверяются во вложенных областях; новых объявлений внутри них синтаксис HW2 не содержит.

Необъявленное имя даёт `UNKNOWN_NAME`. Отдельно отслеживается множество переменных, которым гарантированно присвоено значение. Параметры и переменные кванторов входят в это множество сразу, остальные переменные — только после корректного присваивания. Чтение до первого присваивания даёт `USE_BEFORE_ASSIGNMENT`, даже при наличии явной аннотации типа. Правая часть группового присваивания проверяется до записи целей.

После `if` берётся пересечение множеств из обеих веток; при отсутствии `else` используется исходное множество для второй ветки. Цикл не гарантирует выполнения тела, поэтому присваивания из тела не становятся гарантированными после цикла. Если именованный результат не присвоен на всех путях к концу тела, выдаётся `UNASSIGNED_RETURN`. В `ensures` результаты доступны как значения после выполнения функции, поэтому для контракта считаются определёнными.

## Типы и правила

| Конструкция | Ограничение и результат |
| --- | --- |
| Целое число | `int` |
| `true`, `false` | `bool` |
| Переменная | Тип разрешённого символа |
| Унарный `-`, `+ - * /` | Аргументы `int`, результат `int` |
| `< <= > >=` | Аргументы `int`, результат `bool` |
| `== !=` | Одинаковые простые типы, результат `bool` |
| `not`, `and`, `or`, `->` | Аргументы `bool`, результат `bool` |
| `a[i]` | `a: int[]`, `i: int`, результат `int` |
| Внутренний `set(a, i, v)` | `int[] × int × int → int[]` |
| `length(a)` | `int[] → int` |
| Вызов функции | Проверка количества и типов аргументов, результат по сигнатуре |
| Вызов формулы | Проверка аргументов, результат `bool` |
| Несколько результатов | Внутренний тип `tuple(T1, …, Tn)`; сопоставление целям присваивания |
| Квантор | Типизированная связанная переменная, тело и результат `bool` |
| Контракт, условие, `assert`, `assume` | Требуется `bool` |
| Присваивание | Унификация типа цели с типом соответствующего результата |

Явные аннотации исходного языка: `int`, `int[]`. Логический тип используется для выражений и может выводиться у локальной переменной из вызова формулы. Функциональный тип хранит списки типов параметров и результатов; функции и формулы не являются значениями первого класса.

## Унификация и бонусный вывод

`Types.unify` сопоставляет простые типы по равенству, сигнатуры и кортежи — структурно, с проверкой длины и каждого компонента. Неизвестный тип `?` объединяется с известным; несовместимость возвращает `error`. Неявных приведений, полиморфизма и обобщения типов нет.

У локальной переменной без аннотации начальный тип `?`. Первое корректное присваивание фиксирует её тип; последующие присваивания должны быть совместимы. При ошибочной правой части тип не выводится. Например, после ошибочного `x = length(1)` допустимое `x = a`, где `a: int[]`, всё ещё выводит `x: int[]`. Ошибка первого вызова при этом сохраняется в списке диагностик.

Вывод не решает уравнения по будущим использованиям: `x = y; y = 1;` не позволяет вывести `x`, так как первое чтение `y` ошибочно. Неиспользованная локальная переменная без корректного присваивания также даёт `CANNOT_INFER`. Типы согласуются между ветвями, а гарантированность присваивания проверяется отдельно: присваивание только в одной ветке может определить тип, но не разрешает чтение после `if`.

## Диагностика

Сообщения содержат код, описание и позицию токена: `строка:столбец: [КОД] сообщение`. У повторного объявления также указывается позиция первого. Проверка продолжается после ошибок, включая остальные аргументы, операторы и определения. Тип `error` распространяется вверх по выражению и подавляет производные сообщения о несовместимости типов.

Основные коды: `UNKNOWN_NAME`, `DUPLICATE_NAME`, `USE_BEFORE_ASSIGNMENT`, `TYPE_MISMATCH`, `ARGUMENT_COUNT`, `RESULT_COUNT`, `NOT_VARIABLE`, `NOT_CALLABLE`, `IMMUTABLE_PARAMETER`, `DUPLICATE_TARGET`, `CANNOT_INFER`, `UNASSIGNED_RETURN`. При прямом построении AST также проверяется обязательность и допустимость аннотаций (`MISSING_TYPE`, `UNSUPPORTED_TYPE`).

## Аннотированный AST для HW4

API:

```java
Parser.Result parsed = new Parser(source).parse();
if (!parsed.errors().isEmpty()) {
    throw new IllegalArgumentException(parsed.errors().toString());
}
SemanticAnalyzer.Result checked = SemanticAnalyzer.analyze(parsed.module());
if (!checked.diagnostics().isEmpty()) {
    throw new IllegalArgumentException(checked.diagnostics().toString());
}
System.out.println(AstPrinter.print(checked));
```

`checked.module()` содержит исходный AST. `types()` хранит тип каждого выражения, в том числе целей присваиваний и внутренних узлов `Update`. `bindings()` связывает объявления, имена и вызовы с символами. `symbols()` содержит идентификатор, имя, вид, итоговый тип и токен объявления каждого символа. Таблицы и списки результата доступны только для чтения; таблицы узлов используют идентичность объектов, а не структурное равенство records. Из токена можно получить смещение, строку и столбец.

Текстовый формат — S-выражения версии 1:

```text
(typed-ast 1
  (symbols (symbol #0 builtin length (func (int[]) (int)) @1:1) ...)
  (module ...))
```

Выражение: `(: TYPE @line:column SYMBOL NODE)`. `SYMBOL` — `#id` разрешённого имени/вызова либо `_`. Объявление переменной: `(name TYPE @line:column #id)`. Простые типы — атомы `int`, `bool`, `int[]`; сигнатура — `(func (PARAM_TYPES) (RETURN_TYPES))`; кортеж — `(tuple TYPE ...)`. `?` обозначает невыведенный тип, `error` — ошибочное выражение. Полный результат минимальной программы зафиксирован в `examples/minimal.typed.ast`. Идентификаторы символов детерминированы в пределах одного анализа и различают затенённые имена.

Перед генерацией IR или кода нужно проверить, что оба списка ошибок пусты. При синтаксической ошибке CLI выдаёт частичный обычный AST и не запускает семантический этап.

## Тесты и ограничения

Сохраняются тесты HW2. Дополнительные тесты покрывают положительную программу со всеми конструкциями, отрицательную программу с точными ожидаемыми сообщениями, снимок аннотированного AST, области видимости и затенение, рекурсию, все группы типов, массивы, сигнатуры, групповые присваивания, определённость присваиваний и бонусный вывод. Отдельно проверяется CLI: файл и стандартный ввод, потоки результата и ошибок, коды завершения и режим `--parse-only`.

Синтаксис HW2 сохранён: `bool` и `string` нельзя писать в аннотациях, `true` нельзя напрямую присвоить переменной, голое логическое имя нельзя использовать как предикат, вызов формулы нельзя напрямую использовать как условие `if`. Контракты не допускают импликацию, условия допускают её. Формулы допускают кванторы. Многомерные массивы, строки, перегрузки, преобразования и локальные объявления внутри блока отсутствуют. Вложенное индексирование разбирается парсером, но отклоняется типизацией.

Анализ консервативен: не вычисляет константные условия, не доказывает истинность контрактов, границы индексов, отсутствие деления на ноль или завершение циклов. Размер и значения целых чисел не проверяются на этом этапе.
